# Spec T183: API Đánh dấu Cảnh báo Đã Tiếp Nhận (Acknowledge Alert)

## 1. Mục tiêu
Cho phép thủ kho (hoặc người dùng hợp lệ) xác nhận rằng họ đã thấy và đang xử lý cảnh báo tồn kho (chuyển trạng thái từ `OPEN` sang `ACKNOWLEDGED`).

## 2. API Contract
- **Endpoint**: `PUT /api/inventory-alerts/{id}/acknowledge`
- **Method**: `PUT` (Tính chất Idempotent)
- **Security**: Yêu cầu JWT hợp lệ.
- **Path Variable**: `id` (Long) - ID của InventoryAlert.
- **Request Body**: Không cần (Theo nguyên tắc Ponytail/YAGNI).
- **Response Body**: `InventoryAlertResponse` (Trả về DTO thông tin mới nhất).

## 3. Logic Nghiệp vụ & State Transition
Dựa trên kết quả chốt phương án với User:

### State Diagram
```text
  OPEN
   │
   │ (acknowledge)
   ▼
ACKNOWLEDGED
   │
   │ (resolve)
   ▼
RESOLVED
```

1. **Authentication & Authorization**: 
   - Lấy tên người dùng hiện tại (username) từ Authentication Context (VD: thông qua `SecurityContextHolder` hoặc `@AuthenticationPrincipal`).

2. **Truy xuất Entity**: 
   - Tìm bằng `InventoryAlertRepository.findById(id)`. 
   - Nếu không tồn tại: ném `ResourceNotFoundException` (Mapped to `404 Not Found`).

3. **Kiểm tra State Transition**:
   - Nếu `status == RESOLVED`: Ném ngoại lệ custom `InvalidAlertStateException`, GlobalExceptionHandler sẽ map thành `400 Bad Request`.
   - Nếu `status == ACKNOWLEDGED`: Bỏ qua cập nhật (Idempotent), giữ nguyên `handledBy` cũ, **không gọi `repository.save()`**. Trả về `200 OK`.
   - Nếu `status == OPEN`: Cập nhật trạng thái thành `ACKNOWLEDGED` và gán `handledBy` = username. (Trường `updatedAt` tự động update do Entity đang dùng `@UpdateTimestamp` / JPA Auditing).

4. **Lưu & Trả về**:
   - Gọi `repository.save(alert)` (chỉ khi có thay đổi).
   - Tái sử dụng logic mapping thông qua `InventoryAlertMapper.toResponse(entity)` (Tránh để DTO bị kẹp dependency với Entity).

## 4. Acceptance Criteria

**Case 1: Thành công (OPEN -> ACKNOWLEDGED)**
- Given: Alert đang ở trạng thái OPEN.
- When: Client gọi API.
- Then: 
  - Status đổi thành ACKNOWLEDGED.
  - `handledBy` lưu thành tên user hiện tại.
  - `repository.save()` được gọi.
  - HTTP 200 OK kèm theo DTO được cập nhật.

**Case 2: Idempotent (ACKNOWLEDGED -> ACKNOWLEDGED)**
- Given: Alert đã ở trạng thái ACKNOWLEDGED (có thể bởi người khác).
- When: Client gọi API.
- Then: 
  - Status và `handledBy` giữ nguyên (không bị ghi đè).
  - **Không gọi** `repository.save()`.
  - HTTP 200 OK kèm theo DTO.

**Case 3: Trạng thái không hợp lệ (RESOLVED -> Lỗi)**
- Given: Alert đang ở trạng thái RESOLVED.
- When: Client gọi API.
- Then: 
  - Ném lỗi custom `InvalidAlertStateException`.
  - **Không gọi** `repository.save()`.
  - HTTP 400 Bad Request.

**Case 4: Không tìm thấy Alert**
- Given: ID truyền vào không tồn tại.
- When: Client gọi API.
- Then: 
  - Ném lỗi `ResourceNotFoundException`.
  - **Không gọi** `repository.save()`.
  - HTTP 404 Not Found.

## 5. Non-functional Requirements & Constraints
- **Transaction**: Method ở Service bắt buộc dùng `@Transactional`. Không đặt ở Controller. Tránh transaction lồng nhau.
- **Performance**: 
  - Đúng 1 câu DB SELECT (`findById`).
  - Tối đa 1 câu DB UPDATE (nếu có thay đổi state).
  - Không N+1 query (vì chỉ thao tác trên một Entity và ID đã biết).
- **Concurrency**: Không xử lý concurrent update riêng lẻ ở API này. Sẽ sử dụng mặc định transaction isolation của DB, không thêm Optimistic Locking phức tạp ở scope T183.

## 6. Thiết kế Mã nguồn
- **Controller**: Bổ sung `acknowledgeAlert(@PathVariable Long id)` vào `InventoryAlertController`. Không transactional.
- **Service**: Tạo `InventoryAlertActionService` và `InventoryAlertActionServiceImpl`. Phân rẽ hoàn toàn Write/Action với Query.
- **DTO/Mapper**: Tạo `InventoryAlertMapper` để tái sử dụng mapping logic, chuyển code từ `InventoryAlertQueryServiceImpl` sang.
- **Exception**: Thêm `InvalidAlertStateException` trong package `exception`.
- **Unit Test**: Đảm bảo Mockito `verifyNoMoreInteractions(repository)` hoặc `verify(repository, never()).save(any())` ở các case Idempotent và lỗi.
